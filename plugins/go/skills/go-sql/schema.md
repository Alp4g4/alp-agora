# Schema

The schema stores what the application decided. It never decides anything itself: no generated values, no defaults, no value checks, no business logic. It guards the structure of the data (types, `NOT NULL`, keys, uniqueness) and makes the application's queries fast (indexes). Validating values is the domain's job.

## Must contain

- **A primary key on every table**, a column named `id` holding a UUID v7: `uuid` in PostgreSQL, `TEXT` holding the canonical UUID string in SQLite.
- **`created_at` and `updated_at` on every table**, both `NOT NULL`, set by the application.
- **`NOT NULL` on every column**, unless "no value" is a real state of the data (`email_verified_at` is `NULL` until the email is verified).
- **Timestamps with time zone**: `timestamptz` in PostgreSQL, a `TIMESTAMP` column holding UTC with its offset in SQLite.
- **Foreign keys** for every reference to another table, with an explicit `ON DELETE`.
- **Unique constraints** where the data must not repeat (`email`).
- **Indexes** for every query the application runs, and for every foreign key column.

## Must never contain

- **Default values.** No `DEFAULT`, not even `DEFAULT now()`, `DEFAULT gen_random_uuid()`, or `DEFAULT false`. The application supplies every value: IDs and time come from the use case, so the stored row is exactly what the domain decided, and a missing value fails the insert instead of being silently filled.
- **Enum types.** No `CREATE TYPE ... AS ENUM`. A closed set of values (`status`) is a `text` column, and the domain type (`order.Status`) defines its values.
- **`CHECK` constraints.** No check on a value (`status IN (...)`, `amount >= 0`, `length(currency) = 3`). The domain validates values with `ParseX`, once, at the boundary. A second copy of the rule in the schema drifts from the first, and changing it costs a migration.
- **Soft delete.** No `deleted_at` or `is_deleted`. A deleted row is removed with `DELETE`.
- **Timestamps without time zone.** No `timestamp` / `timestamp without time zone` in PostgreSQL, no local time or missing offset in SQLite.
- **Auto-increment IDs.** No `serial`, `bigserial`, `GENERATED ... AS IDENTITY`, or `AUTOINCREMENT`. IDs are UUIDs generated by the application.
- **Business logic in the database.** No triggers, stored procedures, or rules that change data or enforce a business rule. The domain owns the rules.
- **Quoted identifiers.** No `"user"` or `"order"`: names are chosen so they never need quotes.
- **Search on JSON columns.** A JSON column is never filtered, joined, sorted, or indexed on. If a query needs a value inside it, that value is a column.
- **Types for display or one engine's habits**: no `money` type, no floating point for amounts, no `varchar(255)` by reflex.

## Design rules

1. **Table names are lowercase, singular, and snake_case.** `user_account`, `order_item`, not `Users` or `orderItems`. A table describes one row.
2. **Never use a reserved word as a name.** A reserved word is a word of the SQL language itself (`user`, `order`, `group`, `select`, `table`): `CREATE TABLE order` is a syntax error. Choose a more specific noun (`user_account`, `customer_order`, `user_group`), never quotes. The same applies to columns (`order`, `user`, `default`).
3. **Column names are lowercase snake_case**, named after what they hold:
   - a foreign key is `<referenced table>_id` (`user_account_id`)
   - a timestamp is `<event>_at` (`created_at`, `email_verified_at`)
   - a duration or a quantity carries its unit (`timeout_seconds`, `amount_minor`)
4. **No default values.** See "Must never contain". This also applies to `created_at` and `updated_at`: the use case sets them from its clock.
5. **IDs are UUID v7, generated by the use case** (`uuid.NewV7()`). A v7 UUID starts with its creation time, so new rows go to the end of the primary key index instead of a random place. Inserts stay fast and the index stays compact as the table grows.
6. **Every table has `created_at` and `updated_at`.** The use case sets both on insert and `updated_at` on every update, from its clock. Child tables (`order_item`) have them too.
7. **`NOT NULL` is the default; `NULL` must mean something.** A nullable column is a real "not yet" or "not applicable", the same as a pointer field in the domain entity. Never use `NULL` and an empty string for the same meaning.
8. **A timestamp instead of a boolean, whenever possible.** `email_verified_at` tells whether and when, `is_verified` only whether. Use a boolean only for a state that has no moment (`is_admin`, a setting).
9. **Store values in the shape of the domain.** Amounts are integers in minor units with a currency column (`amount_minor`, `currency`), as the domain `Money`. A closed set of values is `text`, holding the values of the domain type. Column types match the persistence model, so the infrastructure model can be cast to the entity.
10. **Name every constraint and index**, so errors and migrations can refer to them:

    | Kind | Name |
    |---|---|
    | primary key | `pk_<table>` |
    | foreign key | `fk_<table>_<column>` |
    | unique | `uq_<table>_<columns>` |
    | index | `idx_<table>_<columns>` |

    The infrastructure layer matches the unique constraint name to translate a violation into an application error (`uq_user_account_email` → `ErrEmailAlreadyExists`).
11. **Index every foreign key column.** Neither engine does it automatically, and a missing index makes joins and `ON DELETE` checks scan the whole child table.
12. **Index for the queries, not for the columns.** Read the queries the application runs (the `.sql` files of `queries.md`) and give each `WHERE`, `JOIN`, and `ORDER BY` an index:
    - **Composite index order:** equality columns first, then range or sort columns. `WHERE user_account_id = ? AND created_at > ? ORDER BY created_at` → `(user_account_id, created_at)`.
    - **Keyset pagination:** end the index with the same columns as the `ORDER BY`, `id` included. `ORDER BY created_at DESC, id DESC` after `WHERE user_account_id = ?` → `(user_account_id, created_at, id)`. The page is then read straight from the index, with no sort step.
    - **Leftmost prefix:** an index on `(a, b)` also serves queries on `a` alone. Do not add a separate index on `a`.
    - **A unique constraint is already an index.** Do not index the same columns again.
    - **Every index slows writes.** Do not index a column no query filters, joins, or sorts on.
13. **Delete for real: `CASCADE` inside an aggregate, `RESTRICT` between aggregates.** The `ON DELETE` of a foreign key follows the aggregate boundary:
    - **Inside an aggregate** (`order_item` → `customer_order`): `ON DELETE CASCADE`. The child is a part of its root and means nothing without it, so deleting the root deletes its parts in the same statement.
    - **Between aggregates** (`customer_order` → `user_account`): `ON DELETE RESTRICT`. Deleting a user must never silently delete their orders. The delete fails while references exist.
    - **Never `SET NULL` or `SET DEFAULT`.** The database does not decide what happens to the other aggregate: there are no defaults, and a `NULL` would appear without the domain choosing it.

    If the history of deleted data matters, it is a business concept with its own table (an audit log), not a flag.
14. **JSON only for data the database never looks into.** `jsonb` in PostgreSQL, `TEXT` holding JSON in SQLite, for a payload stored and read back whole (a raw webhook body, user preferences). Never in a `WHERE`, a `JOIN`, an `ORDER BY`, or an index.
15. **Normalize first.** One fact in one place (third normal form). Denormalize only for a measured performance need, and document why in the migration.
16. **Tables follow the aggregates of the domain.** An aggregate is a root entity and the parts that only exist through it (`Order` and its `Item`s), loaded and saved as one unit.
    - **One table for the root, one child table per kind of part**: `customer_order` and `order_item`. The child table holds the root's ID (`customer_order_id`), never the other way around.
    - **Another aggregate is referenced by its ID only**, as the domain does (`Order.UserID` → `customer_order.user_account_id`). Never copy its columns into the table.
    - **Always declare the foreign key, between aggregates too.** One application, one database: the key costs nothing and catches an orphan reference the moment a bug creates it. A foreign key only checks that the ID exists, it never changes the other aggregate. Drop it only if the two tables move to separate databases, where a key cannot exist.
    - **Deleting across aggregates is the use case's decision.** With `RESTRICT`, removing a user who has orders means deleting or reassigning the orders first, then the user. The use case deletes them itself, never by relying on `CASCADE`.
17. **Text without an arbitrary length.** Use `text`. A length limit is a domain rule, enforced by `ParseX`.

## Quick check

Before adding a table or a column, ask:

1. Is there a `DEFAULT`, a `CHECK`, an enum type, a generated ID, or a trigger? If so, the value or the rule belongs to the application.
2. Does the table have `id`, `created_at`, and `updated_at`, and is every other column `NOT NULL` or has its `NULL` a meaning?
3. Is every timestamp with time zone, and every ID the engine's UUID type?
4. Does every query and every foreign key have an index, with the columns of composite indexes in the right order?
5. Is the table name lowercase, singular, not a reserved word, and are the constraints named?
