# Queries with sqlc

Queries are written in SQL, in `.sql` files, and sqlc generates the Go code that runs them. The generated code is an infrastructure detail: a store in the infrastructure layer calls it, casts the result to the domain entity, and implements the application's ports. Nothing outside infrastructure knows sqlc exists.

The tables come from `schema.md`, and the schema sqlc reads is the migrations folder of the engine (`migrations.md`).

## Layout

```
sqlc.yaml                          # one sql block per engine in use
internal/infrastructure/postgres/
├── migrations/                    # the schema sqlc reads (migrations.md)
├── queries/
│   ├── user_account.sql           # one file per table
│   └── customer_order.sql
├── sqlcgen/                       # generated by sqlc: never edited
│   ├── db.go
│   ├── models.go
│   └── user_account.sql.go
└── user_store.go                  # implements the ports, casts sqlcgen.UserAccount to user.User
```

## Must contain

- **One `.sql` file per table**, each query with a `-- name: <Name> :<kind>` annotation.
- **The full column list of the table**, in the table's order, in every `SELECT` on one table, so sqlc returns its generated model.
- **Named parameters**: `@name`, and `sqlc.narg(name)` for a parameter that can be `NULL`.
- **Overrides in `sqlc.yaml`** mapping columns to the Go types of the domain (`uuid.UUID`, `time.Time`, `*time.Time`, value objects such as `user.Email`), so the generated model has the shape of the entity.
- **A `@limit_count` on every list query**, with keyset pagination.
- **An index behind every `WHERE`, `JOIN`, and `ORDER BY`**, as `schema.md` defines them.

## Must never contain

- **`SELECT *`**, not even with sqlc. Every column is written out.
- **Positional parameters**: no `$1`, `$2`, or `?`.
- **Unbounded queries**: no list query without a limit.
- **`UPDATE` or `DELETE` without a `WHERE`.**
- **Dynamic SQL**: no string concatenation, no query built at runtime. sqlc can only check the SQL it sees.
- **Edits to generated code.** Change the query or `sqlc.yaml`, then run `sqlc generate`.
- **Generated types outside infrastructure.** `sqlcgen.UserAccount` and the `Params` and `Row` structs never appear in a port signature. Ports take and return domain types.

## Design rules

1. **Name queries after their intent**, with the table in the name: `GetUserAccount`, `GetUserAccountByEmail`, `ListUserAccounts`, `ListCustomerOrdersByUserAccount`, `CreateUserAccount`, `UpdateUserAccount`, `DeleteUserAccount`. `Get` returns one row, `List` several.
2. **Choose the annotation from what the store needs back:**

   | Query | Annotation |
   |---|---|
   | one row | `:one` |
   | several rows | `:many` |
   | insert | `:exec` |
   | update, delete | `:execrows` |

   `:execrows` returns the number of affected rows. 0 means the row does not exist, so the store returns its not-found error without reading the row first.
3. **Select every column of the table, in the table's order.** When the result columns are exactly the table's columns, sqlc returns its model (`UserAccount`) instead of generating a `Row` struct. With the overrides, the model has the same fields as the entity, and the store casts it (`user.User(m)`). Writing the columns out keeps the query readable and makes a schema change visible in the query's diff.
4. **Aliases only with a join.** A query on one table uses no alias. A join aliases every table with its initials (`user_account u`, `customer_order co`, `order_item oi`) and prefixes every column (`co.status`, `u.email`). A join result is a `Row` struct, so the store maps it (a cast is not possible).
5. **Named parameters only.** `WHERE id = @id`, `SET avatar_key = sqlc.narg(avatar_key)`. The generated `Params` struct then has real field names (`ID`, `AvatarKey`) instead of `Column1`.
6. **Overrides make the model match the entity.** In `sqlc.yaml`, map the engine types (`uuid`, `timestamptz`) and then the columns that hold a domain value object (`user_account.email` → `user.Email`, `user_account.password_hash` → `user.PasswordHash`). Nullable columns become pointers. If an override is missing, the cast stops compiling and points at the field to fix.
7. **Never read a whole table.** Every `:many` query takes `@limit_count`. The use case applies the default (100) and the maximum (1000), so the value is visible and tested, and the SQL never hard-codes it. Exceptions, which need no limit:
   - a lookup by primary or unique key (`:one`)
   - `COUNT` and other aggregates
   - the parts of one aggregate loaded with their root (`order_item` of one order), bounded by the aggregate itself
8. **Paginate with a keyset, never with `OFFSET`.** `OFFSET 10000` still reads and discards 10,000 rows. IDs are UUID v7, so they sort by creation time: `WHERE id < @cursor ORDER BY id DESC LIMIT @limit_count` is fast at any depth and uses the primary key. The first page passes the largest UUID (`uuid.Max`). To sort on another column, compare the pair `(created_at, id)` with the cursor and `ORDER BY created_at DESC, id DESC`, and give it an index ending with `id` (`schema.md`). sqlc types every parameter of a row comparison as its first column, so the syntax differs per engine: see `references/queries-postgres.md` and `references/queries-sqlite.md`.
9. **Every `LIMIT` has an `ORDER BY` that ends with a unique column** (`id`). Without it, the order of equal rows changes between calls and pages repeat or skip rows.
10. **Every filter has an index.** Each column in a `WHERE`, `JOIN`, or `ORDER BY` is covered by an index from `schema.md` (the primary key, a unique constraint, or an index whose leftmost columns match). If none covers it:
    - **in a conversation**, ask whether to add the index before writing the query
    - **in an automated pipeline**, add the index in the ticket's migration, following `schema.md`, and list it in the pull request description under "Indexes added"
11. **`INSERT` lists every column; `UPDATE` sets every column but `id` and `created_at`.** There are no defaults, so the row holds exactly what the entity holds. An `UPDATE` that sets every column saves the whole entity, as the store's `UpdateUser(ctx, u)` method does.
12. **No N+1.** Never run one query per parent in a loop. Load the children of several parents in one query: `= ANY(@ids::uuid[])` in PostgreSQL, `IN (sqlc.slice(ids))` in SQLite.
13. **One query per filter the application uses.** A different filter is a different named query, not a runtime condition. Avoid catch-all filters such as `(sqlc.narg(email) IS NULL OR email = sqlc.narg(email))`: one plan serves every combination and the index is often skipped.
14. **Generated code stays in infrastructure.** `sqlcgen` is imported only by the store of its engine. The store turns the generated model into the domain entity before returning.
15. **Keep the generated code in sync.** Commit the generated files. In CI, run `sqlc generate` then `git diff --exit-code`, so a query changed without regenerating fails the build, and `sqlc vet` to check the queries against the schema.

## Quick check

Before adding a query, ask:

1. Does it list every column instead of `*`, in the table's order, so it returns the model?
2. Are all parameters named (`@name`, `sqlc.narg`)?
3. If it returns several rows, does it take `@limit_count`, use a keyset, and end its `ORDER BY` with `id`?
4. Is every column in its `WHERE`, `JOIN`, and `ORDER BY` covered by an index?
5. Does an `UPDATE` or `DELETE` have a `WHERE` and use `:execrows`?
6. Does any generated type leave the infrastructure package?
