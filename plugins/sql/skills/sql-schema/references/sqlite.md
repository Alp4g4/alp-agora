# SQLite

The rules of `sql-schema` applied to SQLite. SQLite has few types and, by default, does not enforce them: these rules make it strict.

## Make it strict

- **Every table is `STRICT`** (SQLite 3.37 or later). Without it, a column declared `INTEGER` accepts `'abc'`. A `STRICT` table only allows `INTEGER`, `REAL`, `TEXT`, `BLOB`, and `ANY`, and rejects a value of the wrong type. This is a type check, not a `CHECK` constraint: it stays.
- **Foreign keys are off by default.** Turn them on for every connection with `PRAGMA foreign_keys = ON`, usually through the driver's connection string (`_pragma=foreign_keys(1)`). The pragma cannot go in a migration: it applies to one connection, not to the database file.

## Types

| Value | Type | Content |
|---|---|---|
| ID | `TEXT` | the canonical lowercase UUID v7 string, `019a6c3e-8d2a-7c39-9a57-3f1e2d4c6b80` |
| timestamp | `TEXT` | the instant in UTC, with its offset, as the driver writes a `time.Time` |
| text | `TEXT` | |
| boolean, only when no timestamp fits | `INTEGER` | `0` or `1` |
| integer | `INTEGER` | 64-bit |
| amount | `INTEGER` in minor units, plus `currency TEXT` | never `REAL` |
| closed set of values | `TEXT` | the values of the domain type |
| payload never searched | `TEXT` holding JSON | never read with the `json_*` functions in a query |

- **UUIDs as text.** SQLite has no UUID type. `uuid.UUID` from google/uuid writes the canonical lowercase string and reads it back, so the infrastructure model keeps `uuid.UUID` and the cast to the entity still works. A v7 UUID string starts with its timestamp, so it also sorts in creation order.
- **Timestamps always in UTC.** SQLite has no date type: a timestamp is text, compared and sorted as text. Text sorts in time order only if every value has the same format and the same offset. The use case passes UTC, so every stored value ends with the same offset.
- **No `AUTOINCREMENT`, no `INTEGER PRIMARY KEY` for IDs.** An `INTEGER PRIMARY KEY` becomes an alias of the row ID and is generated by SQLite. IDs are UUIDs from the application.
- **Reserved words** include `order`, `group`, `table`, `default`, `limit`, `offset`, `end`. `user` is not reserved in SQLite but is in PostgreSQL: avoid both lists, so a schema can move between the two engines. The full list is in the SQLite documentation, "SQL Keywords".

## Example: user_account

The domain `user.User` from `go-clean-arch-domain`.

```sql
CREATE TABLE user_account (
    id                TEXT NOT NULL,
    email             TEXT NOT NULL,
    email_verified_at TEXT,          -- NULL until the email is verified
    password_hash     TEXT NOT NULL,
    avatar_key        TEXT,          -- NULL when the user has no avatar
    created_at        TEXT NOT NULL,
    updated_at        TEXT NOT NULL,

    CONSTRAINT pk_user_account PRIMARY KEY (id),
    CONSTRAINT uq_user_account_email UNIQUE (email)
) STRICT;
```

## Example: customer_order and order_item

`order` is reserved, so the root table is `customer_order`.

```sql
CREATE TABLE customer_order (
    id              TEXT NOT NULL,
    user_account_id TEXT NOT NULL,
    status          TEXT NOT NULL, -- values of order.Status, validated by the domain
    created_at      TEXT NOT NULL,
    updated_at      TEXT NOT NULL,

    CONSTRAINT pk_customer_order PRIMARY KEY (id),
    CONSTRAINT fk_customer_order_user_account_id
        -- between two aggregates (Order → User): RESTRICT
        FOREIGN KEY (user_account_id) REFERENCES user_account (id) ON DELETE RESTRICT
) STRICT;

-- "orders of a user, newest first", and the foreign key as leftmost column
CREATE INDEX idx_customer_order_user_account_id_created_at
    ON customer_order (user_account_id, created_at);

CREATE TABLE order_item (
    id                TEXT    NOT NULL,
    customer_order_id TEXT    NOT NULL,
    product_id        TEXT    NOT NULL,
    quantity          INTEGER NOT NULL,
    unit_price_minor  INTEGER NOT NULL,
    currency          TEXT    NOT NULL,
    created_at        TEXT    NOT NULL,
    updated_at        TEXT    NOT NULL,

    CONSTRAINT pk_order_item PRIMARY KEY (id),
    -- inside the Order aggregate: CASCADE
    CONSTRAINT fk_order_item_customer_order_id
        FOREIGN KEY (customer_order_id) REFERENCES customer_order (id) ON DELETE CASCADE
) STRICT;

CREATE INDEX idx_order_item_customer_order_id ON order_item (customer_order_id);
```

## Limits specific to SQLite

- **Foreign keys are not indexed automatically**, as in PostgreSQL. Add the index.
- **`ALTER TABLE` is limited.** It can add, rename, and drop a column, but cannot change a column's type, add a constraint, or make a column `NOT NULL`. Those changes rebuild the table (create the new table, copy, drop, rename). That is a migration concern, see `sql-migrations`.
- **Adding a `NOT NULL` column to a table with rows** requires a default in SQLite, which this skill forbids. Add the column as part of a table rebuild, where the copy supplies the value.
- **Case-insensitive comparison**: `COLLATE NOCASE` only folds ASCII letters. Normalize values in the domain (`ParseEmail` lowercases the email) rather than relying on it.
- **Partial indexes** work as in PostgreSQL (`CREATE INDEX ... WHERE status = 'pending'`).
